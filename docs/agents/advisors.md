# Advisors, lints, and the hosted database's out-of-band steps

How schema work in this repo passes its gates. [ADR-0023](../adr/0023-the-v1-schema-is-ten-household-owned-tables-under-pair-keys-with-three-granted-definer-rpcs-as-its-whole-privileged-surface.md) decided the schema; this file is what a ticket touching `supabase/` must know to ship it. Facts below were verified against the Supabase docs and CLI 2.122.0 for [ticket #3](https://github.com/justintaddei/kinetic-lists/issues/3).

## The two gates, and what each sees

- `supabase db lint` runs **`plpgsql_check` over function bodies only**. It does not see tables, policies, grants, views, triggers or indexes. It is a plpgsql linter, nothing more.
- `supabase db advisors` prints the Supabase **advisor** findings — the security and performance rules [the advisory registry](https://supabase.com/docs/guides/database/advisors) names (`0001`…`0030`), the same registry Supabase Studio's **Advisor rules** page shows against the hosted project, since [2026-06](https://supabase.com/changelog.md/2026-06-22-advisor-api) on `plpgsql_check` findings too.
- Both gates need a shadow database, so both run in CI on a local stack ([#4](https://github.com/justintaddei/kinetic-lists/issues/4)), and nothing about them can be checked by a `git commit` alone.

## The suppression contract

`preview_invitation` is granted to `anon`, and the three RPCs are granted to `authenticated`; all three are `security definer`. Lint `0029` fires on them **by design** — [ADR-0023](../adr/0023-the-v1-schema-is-ten-household-owned-tables-under-pair-keys-with-three-granted-definer-rpcs-as-its-whole-privileged-surface.md): *the grant is the app's API surface; a definer the phone cannot call is not an API.* The set is closed: nothing else gets a grant, and the app's PostgREST-exposed functions stay exactly:

- `public.buy_basket(uuid, uuid, date, text)` → `authenticated`
- `public.join_household(uuid)` → `authenticated`
- `public.preview_invitation(uuid)` → `anon`, `authenticated`
- `public.uuidv7()` → `authenticated`, `service_role` — `security invoker`, so 0028/0029 cannot fire on it (their engine reads `prosecdef`), and an id default runs as the inserting role; it is not an RPC and is not in the API's function set
- `private.is_member(uuid)` → `authenticated`, and `private.handle_new_user()` → `supabase_auth_admin` — `security definer`, in `private`, the schema `[api] schemas = ["public", "graphql_public"]` never exposes; `private`'s ACL is measured in the generated tree, and the sign-up grant is ADR-0019's mechanism, not an HTTP surface

Suppressions live in the hosted project, not in this repo: the CLI has no in-repo expression for an advisory suppression, so they are applied per object on the hosted project's **Advisor rules** page (Supabase Studio → **Database → Advisor rules**), and re-checked after every `db push`. They are out-of-band state on hosted, so:

- Suppressions are **not** reapplied by `db reset` (that is a local-stack operation — it is *how* #4's CI builds a shadow database, and it touches no hosted project from a checkout. The hosted database is never reset from a checkout; it moves by migration.)
- #4's CI gate is: `db lint` clean, `supabase db advisors` reviewed against this register, and `db schema declarative sync --no-apply` writing a migration whose SQL the review reads (`sync` has no `--dry-run` flag — `--no-apply` is the non-destructive form, and it leaves the file in `supabase/migrations/` for `git diff` to show).
- A new `security definer` function reaching `anon`/`authenticated` is a decision, and joins this list by being written here first, in the same PR that adds it.

## The declarative schema and the demo table's retirement

`supabase/schemas/*.sql` is the source of truth (`[experimental.pgdelta] enabled = true` in [`supabase/config.toml`](../../supabase/config.toml)), and `supabase db schema declarative sync` mints a migration from the diff — `--no-apply` to write the file without touching a database (`--apply`/`--yes` applies it to the local stack), `--file` to save the diff as a new migration file and `--name` to name it, and **`--strict-coverage` in CI** so any object the engine declines to model fails the build instead of quietly disappearing. There is no `--dry-run` on this subcommand: with `--no-apply` the migration SQL is what you read.

- **File order is automatic under pg-delta** - the CLI orders the declarative files by statement dependency, and `[db.migrations].schema_paths` is ignored (it warns when set). The `01_`…`06_` prefixes in `supabase/schemas/` are reading order for humans, not load order.
- **Permissions are declarable, `alter default privileges` included.** A `db pull --declarative --linked` on hosted (CLI 2.122.0, run 2026-10-31) wrote a manifest-managed tree: `.pgdelta-export.json` (`loadOrder`, `files`, `defaultOwner`), `_cluster/extensions/pgcrypto.sql` + `uuid-ossp.sql`, `public/schema.sql` (schema comment, `revoke all on schema "public"` + `grant usage` per role), `public/adp_wipes.sql` (the `alter default privileges` that clear "assumed destination defaults", so a plan applies on a clean database), `public/default_privileges.sql` (the same ADPs as live state, including `revoke all on functions in schema "public" from public`), and `public/tables/<t>.sql` per table. **Commit the manifest**: it is what makes a generated tree reproducible, and `generate` prunes the rest.
- A generated tree and a hand-written file coexist only as a warning. `db pull` reports `1 existing declarative schema file(s) … are not tracked by an export manifest and were preserved`, and "to regenerate the directory cleanly, remove `supabase/schemas` and re-run `db schema declarative generate`". Steady state is **one generated tree**; the six flat files are the seed that mints the baseline, not a permanent shape.
- **Retirement goes in a migration, not a declarative file**: `db schema declarative sync` deletes a table when you delete its declarative file (so the tree is only trusted once it is a snapshot of the destination), and `db pull` prunes a declarative file whose object is gone — a `drop table` written into the tree vanishes the next time anyone pulls, and history stops being append-only. The demo `lists` table retires through [`supabase/migrations/20261031000000_retire_demo_list.sql`](../../migrations/20261031000000_retire_demo_list.sql); its creation migration stays in `supabase/migrations/`, because a migration in history is history and `db pull` refuses a remote migration with no local file.
- `supabase/schemas/_custom/` is reserved for the objects pg-delta declines to model, and pg-delta names them: casts, operators, operator classes and families, text-search configurations/dictionaries/parsers/templates, statistics objects, languages, transforms, parameter ACLs. **Grant posture is not one of them.** `generate` never creates, overwrites, or prunes that directory, and unmodeled objects are never dropped from the database; each needs a hand-written migration that **sorts before** the generated migration which uses it — a late-sorting one breaks `db reset` on a shadow stack.

The baseline needs no reset, and it needs no hand-applied grants:

Every step runs on a branch cut from an up-to-date `master` — the declarative tree and `supabase/migrations/` are what `sync` reads, so a branch that does not contain them mints the wrong diff. Minting a migration is not the end of the PR: the snapshot in step 3 is of the **pushed** database, so the push sits between steps 1 and 3 inside the same PR.

1. `supabase db schema declarative sync -f add_v1_schema --no-apply` mints the baseline migration from the six seed files (shadow stack: Docker Desktop must be running), CI mints it, and the PR carries it. On a machine whose Docker engine is down the baseline can be minted by hand, and #4 did: `20261101000000_add_v1_schema.sql` is the six seeds concatenated in file order, and that concatenation *is* the plan when the destination is empty and the history is applied on both sides — the file's header carries the measurement and the dependency walk. `sync -f <name>` is the flag (`--file` is shorthand); `sync --name` does not exist.
2. `supabase db push --linked --yes` applies it on hosted — **no password, measured 2026-11-02** on `ohbrawtgcyngyhaqtddy`: the CLI's scoped access token does it, printing `Initialising login role...`; `db query --linked` and `gen types --linked` work the same way. What needs the password (never measured here) is direct Postgres access: `psql`, Studio's SQL Editor. The push failed four times before it landed, and each failed push was a transaction: measured after every one, hosted sat at 0 tables and the same 2 applied versions. `20261031000000_retire_demo_list.sql` is applied (measured 2026-10-31: `migration list --linked` is equal on both sides, hosted's `public` has no tables), so the minted migration carries the twelve tables and nothing else;
3. `rm -rf supabase/schemas` (the seed files are hand-written, so `generate` would only "preserve" them with a warning), then `supabase db schema declarative generate --linked --overwrite` snapshots hosted into the steady-state tree — the generated tree, `.pgdelta-export.json` included, replaces `01_`…`06_` in the same commit, and the types regenerate from the pushed schema (`gen types --linked` needs no Docker; `package.json`'s `db:types` uses `--local` and needs the stack up);
4. from there every change is declarative, and only `sync`'s shadow database sees it: a hand-edit in Studio, psql, or the hosted Integrity check is invisible to the diff engine.

Nothing here resets hosted, and nothing here clears accounts — `select count(*) from "auth"."users"` on hosted is **0** (verified 2026-10-31), since ADR-0019 is unshipped and no sign-up has run against it.

## Grant posture, and the facts that carry no declarable file at all

Signed out, the app reads nothing except `preview_invitation`. The posture is carried by the declarative files themselves: every table and view opens with `revoke all on "<t>" from "anon", public;` and grants select to `authenticated`, and every RPC opens with `revoke all on function "<f>"(…) from public;` before its grants. `public` is in the function revokes because Postgres' own default grants `execute` to `PUBLIC`.

The bulk form is not needed, because hosted's own default privileges are already narrow (`db query --linked` on `pg_default_acl`, 2026-10-31, grantor `postgres`, schema `public`):

```postgres
anon=Dxtm     authenticated=Dxtm     service_role=Dxtm
```

`Dxtm` is `DELETE`,`TRUNCATE`,`REFERENCES`,`TRIGGER`,`MAINTAIN` — **no `insert`, no `select`, no `update`, no function `execute`** — so a table created by a later migration is born granted to nobody but `postgres`. The pull keeps the fact declarable, and `public/adp_wipes.sql` carries the same revokes for the defaults a plan must clear on a clean destination.

`private` carries no grants at all beyond `usage` for `authenticated` and `supabase_auth_admin`, so it has no HTTP surface: PostgREST reaches schemas listed in `[api] schemas = ["public", "graphql_public"]` and nothing else. **`db push --linked` refuses an out-of-order migration** — verified 2026-10-31 with `db push --linked --dry-run` at #23's merge commit: `Found local migration files to be inserted before the last migration on remote database. Rerun the command with --include-all flag to apply these migrations`. A hand-written migration in a schema PR must therefore sort **after** everything applied on hosted; that check is what deleted `20261029000000_posture_grants.sql` (never applied: `migration list --linked` shows `20261030005109` as the only version, local and remote) rather than pushing it with `--include-all`. The platform facts a schema ticket inherits:

- Role settings are not declarable, so `[api] db-aggregates-enabled = false` is the shipped posture: no `count=`/`sum=` in PostgREST queries. [PostgREST: vertical and horizontal filtering](https://docs.postgrest.org/en/v13.1/references/api/tables_views.html#vertical-and-horizontal-filtering).
- [PostgREST: batched requests](https://docs.postgrest.org/en/v13.1/references/api/transactions.html#batched-requests) — two operations in one transaction is **refused** for v1; an atomic multi-table write is a **nested insert**, which PostgREST compiles to a single SQL statement, so it needs no `Prefer: transaction` dependency at all.
- Realtime streams only the tables a publication adds ([Supabase: Realtime publications](https://supabase.com/docs/guides/realtime/technical-references/configuration.md)), and a `DELETE` event carries only the replica identity. `item_store_tags` has a composite key, so it carries `replica identity full`. Publication membership is declared with the schema — pg-delta covers it ([Diff engines: pg-delta and migra](https://supabase.com/docs/guides/deployment/declarative-schema/diff-engines)), so #8 adds tables to the Realtime publication in a declarative file and CI mints it. `replica identity` is not on pg-delta's covered list, so expect a coverage warning on that statement and pass `--strict-coverage` in CI; if it is refused, it goes in `supabase/schemas/_custom/` with a hand-written migration sorting before the generated migration that creates its table.
- Unsupported objects are reported as **coverage warnings** by `db schema declarative sync`, and `--strict-coverage` turns them into CI errors. Anything the engine declines to model lives in the reserved `supabase/schemas/_custom/` directory with its hand-written migration; `generate` never touches that directory, and a `generate` after files are added there overwrites nothing.
- `supabase gen types typescript --local --schema public` regenerates [`app/types/database.types.ts`](../../app/types/database.types.ts) from a stack that has the schema (`pnpm run db:types`, then `pnpm dlx oxfmt` on the unformatted output); every schema PR that changes shape regenerates it, in CI, not by hand. Only the schemas passed to `--schema` get types, so a `private` function is untyped unless `--schema public,private` is passed.
