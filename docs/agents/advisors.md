# Advisors, lints, and the hosted database's out-of-band steps

How schema work in this repo passes its gates. [ADR-0023](../adr/0023-the-v1-schema-is-ten-household-owned-tables-under-pair-keys-with-three-granted-definer-rpcs-as-its-whole-privileged-surface.md) decided the schema; this file is what a ticket touching `supabase/` must know to ship it. Facts below were verified against the Supabase docs and CLI 2.122.0 for [ticket #3](https://github.com/justintaddei/kinetic-lists/issues/3).

## The two gates, and what each sees

- `supabase db lint` runs **`plpgsql_check` over function bodies only**. It does not see tables, policies, grants, views, triggers or indexes. It is a plpgsql linter, nothing more.
- `supabase db advisors` prints the Supabase **advisor** findings — the security and performance rules [the advisory registry](https://supabase.com/docs/guides/database/advisors) names (`0001`…`0030`), the same registry Supabase Studio's **Advisor rules** page shows against the hosted project, since [2026-06](https://supabase.com/changelog.md/2026-06-22-advisor-api) on `plpgsql_check` findings too.
- Both gates need a shadow database, so both run in CI on a local stack ([#4](https://github.com/justintaddei/kinetic-lists/issues/4)), and nothing about them can be checked by a `git commit` alone.

## The suppression contract

`preview_invitation` is granted to `anon`, and the three RPCs are granted to `authenticated`; all three are `security definer`. Lint `0029` fires on them **by design** — [ADR-0023](../adr/0023-the-v1-schema-is-ten-household-owned-tables-under-pair-keys-with-three-granted-definer-rpcs-as-its-whole-privileged-surface.md): *the grant is the app's API surface; a definer the phone cannot call is not an API.* The set is closed: nothing else gets a grant, and the app's PostgREST-exposed functions stay exactly:

- `public.buy_basket(uuid, uuid, date, text)` → `authenticated`
- `public.join_household(uuid)` → `authenticated`
- `public.preview_invitation(uuid)` → `anon`, `authenticated`
- `public.uuidv7()` → `authenticated`, `service_role` — `security invoker`, so 0028/0029 cannot fire on it (their engine reads `prosecdef`), and an id default runs as the inserting role; it is not an RPC and is not in the API's function set
- `private.is_member(uuid)` → `authenticated`, and `private.handle_new_user()` → `supabase_auth_admin` — `security definer`, in `private`, the schema `[api] schemas = ["public", "graphql_public"]` never exposes; `private`'s ACL is measured in the generated tree, and the sign-up grant is ADR-0019's mechanism, not an HTTP surface

Suppressions live in the hosted project, not in this repo: the CLI has no in-repo expression for an advisory suppression, so they are applied per object on the hosted project's **Advisor rules** page (Supabase Studio → **Database → Advisor rules**), and re-checked after every `db push`. They are out-of-band state on hosted, so:

- Suppressions are **not** reapplied by `db reset` (that is a local-stack operation — it is *how* #4's CI builds a shadow database, and it touches no hosted project from a checkout. The hosted database is never reset from a checkout; it moves by migration.)
- #4's CI gate is: `db lint` clean, `supabase db advisors` reviewed against this register, and `db schema declarative sync --no-apply` writing a migration whose SQL the review reads (`sync` has no `--dry-run` flag — `--no-apply` is the non-destructive form, and it leaves the file in `supabase/migrations/` for `git diff` to show).
- A new `security definer` function reaching `anon`/`authenticated` is a decision, and joins this list by being written here first, in the same PR that adds it.

## The declarative schema and the demo table's retirement

`supabase/schemas/*.sql` is the source of truth (`[experimental.pgdelta] enabled = true` in [`supabase/config.toml`](../../supabase/config.toml)), and `supabase db schema declarative sync` mints a migration from the diff — `--no-apply` to write the file without touching a database (`--apply`/`--yes` applies it to the local stack), `--file` to save the diff as a new migration file and `--name` to name it, and **`--strict-coverage` in CI** so any object the engine declines to model fails the build instead of quietly disappearing. There is no `--dry-run` on this subcommand: with `--no-apply` the migration SQL is what you read.

- **File order is automatic under pg-delta** - the CLI orders the declarative files by statement dependency, and `[db.migrations].schema_paths` is ignored (it warns when set). The `01_`…`06_` prefixes in `supabase/schemas/` are reading order for humans, not load order.
- **Permissions are declarable, `alter default privileges` included.** A `db pull --declarative --linked` on hosted (CLI 2.122.0, run 2026-10-31) wrote a manifest-managed tree: `.pgdelta-export.json` (`loadOrder`, `files`, `defaultOwner`), `_cluster/extensions/pgcrypto.sql` + `uuid-ossp.sql`, `public/schema.sql` (schema comment, `revoke all on schema "public"` + `grant usage` per role), `public/adp_wipes.sql` (the `alter default privileges` that clear "assumed destination defaults", so a plan applies on a clean database), `public/default_privileges.sql` (the same ADPs as live state, including `revoke all on functions in schema "public" from public`), and `public/tables/<t>.sql` per table. **Commit the manifest**: it is what makes a generated tree reproducible, and `generate` prunes the rest.
- A generated tree and a hand-written file coexist only as a warning. `db pull` reports `1 existing declarative schema file(s) … are not tracked by an export manifest and were preserved`, and "to regenerate the directory cleanly, remove `supabase/schemas` and re-run `db schema declarative generate`". Steady state is **one generated tree**; the six flat files are the seed that mints the baseline, not a permanent shape.
- **Retirement goes in a migration, not a declarative file**: `db schema declarative sync` deletes a table when you delete its declarative file (so the tree is only trusted once it is a snapshot of the destination), and `db pull` prunes a declarative file whose object is gone — a `drop table` written into the tree vanishes the next time anyone pulls, and history stops being append-only. The demo `lists` table retires through [`supabase/migrations/20261031000000_retire_demo_list.sql`](../../migrations/20261031000000_retire_demo_list.sql); its creation migration stays in `supabase/migrations/`, because a migration in history is history and `db pull` refuses a remote migration with no local file.
- `supabase/schemas/_custom/` is reserved for the objects pg-delta declines to model, and pg-delta names them: casts, operators, operator classes and families, text-search configurations/dictionaries/parsers/templates, statistics objects, languages, transforms, parameter ACLs. **Grant posture is not one of them.** `generate` never creates, overwrites, or prunes that directory, and unmodeled objects are never dropped from the database; each needs a hand-written migration that **sorts before** the generated migration which uses it — a late-sorting one breaks `db reset` on a shadow stack.

The baseline needs no reset, and it needs no hand-applied grants:

Every step runs on a branch cut from an up-to-date `master` — the declarative tree and `supabase/migrations/` are what `sync` reads, so a branch that does not contain them mints the wrong diff. Minting a migration is not the end of the PR: the snapshot in step 3 is of the **pushed** database, so the push sits between steps 1 and 3 inside the same PR.

1. `supabase db schema declarative sync -f add_v1_schema --no-apply` mints the baseline migration from the six seed files (shadow stack: Docker Desktop must be running), CI mints it, and the PR carries it. On a machine whose Docker engine is down the baseline can be minted by hand, and #4 did: `20261101000000_add_v1_schema.sql` is the six seeds concatenated in file order, and that concatenation *is* the plan when the destination is empty and the history is applied on both sides — the file's header carries the measurement and the dependency walk. `sync -f <name>` is the flag (`--file` is shorthand); `sync --name` does not exist.
2. `supabase db push --linked --yes` applies it on hosted — **no password, measured 2026-11-02** on `ohbrawtgcyngyhaqtddy`: the CLI's scoped access token does it, printing `Initialising login role...`; `db query --linked` and `gen types --linked` work the same way. What needs the password (never measured here) is direct Postgres access: `psql`, Studio's SQL Editor. The push failed four times before it landed, and each failed push was a transaction: measured after every one, hosted sat at 0 tables and the same 2 applied versions. `20261031000000_retire_demo_list.sql` is applied (measured 2026-10-31: `migration list --linked` is equal on both sides, hosted's `public` has no tables), so the minted migration carries the twelve tables and nothing else;
3. `rm -rf supabase/schemas` (the seed files are hand-written, so `generate` would only "preserve" them with a warning), then `supabase db schema declarative generate --linked --overwrite` snapshots hosted into the steady-state tree — the generated tree, `.pgdelta-export.json` included, replaces `01_`…`06_` in the same commit, and the types regenerate from the pushed schema (`gen types --linked` needs no Docker; `package.json`'s `db:types` uses `--local` and needs the stack up);
4. from there every change is declarative, and only `sync`'s shadow database sees it: a hand-edit in Studio, psql, or the hosted Integrity check is invisible to the diff engine.

Nothing here resets hosted, and nothing here clears accounts — `select count(*) from "auth"."users"` on hosted is **0** (verified 2026-10-31), since ADR-0019 is unshipped and no sign-up has run against it.

## Grant posture, and the facts that carry no declarable file at all

Signed out, the app reads nothing: `anon` holds **no `select` anywhere**, and the one function it executes is `preview_invitation`. The posture is carried by the declarative files: every table and view opens with `revoke all on "<t>" from "anon", public;`, and every RPC opens with `revoke all on function "<f>"(…) from public;` before its grants (`public` is in the function revokes because Postgres' own default grants `execute` to `PUBLIC`).

On the write side the posture is **one grant line per table, naming the verbs its policies open** - measured on hosted 2026-11-03, after `20261103000000_open_the_policy_verbs.sql`:

```postgres
households · household_members      UPDATE
household_invites · item_store_tags INSERT, DELETE
stores · store_locations · items    INSERT, UPDATE, DELETE
lists · list_items                  INSERT, UPDATE      (list_items has no DELETE policy - ADR-0022)
arrivals                            INSERT
purchases · purchase_lines          (none - the append-only denial policies, ADR-0017)
```

RLS decides **which rows** a verb may touch; it never confers the verb, so a policy whose table has no grant is a row filter on a table the role cannot write - `42501`, not an empty result. The baseline shipped `select` only, and the review of #4's own PR found it (`buy_basket` was the one path that worked, because a `security definer` runs as its owner). `anon` also holds `references`, `trigger`, `truncate` and `MAINTAIN` on `public` tables, from `default_privileges.sql`'s ADP line - Supabase's own template, with no Data API route to any of it (measured: anon reaches no table, no function, no sequence).

The bulk form is not needed, because hosted's own default privileges are already narrow (`db query --linked` on `pg_default_acl`, 2026-10-31, grantor `postgres`, schema `public`):

```postgres
anon=Dxtm     authenticated=Dxtm     service_role=Dxtm
```

`Dxtm` is `DELETE`,`TRUNCATE`,`REFERENCES`,`TRIGGER`,`MAINTAIN` — **no `insert`, no `select`, no `update`, no function `execute`** — so a table created by a later migration is born granted to nobody but `postgres`. The pull keeps the fact declarable, and `public/adp_wipes.sql` carries the same revokes for the defaults a plan must clear on a clean destination.

`private` carries no grants at all beyond `usage` for `authenticated` and `supabase_auth_admin`, so it has no HTTP surface: PostgREST reaches schemas listed in `[api] schemas = ["public", "graphql_public"]` and nothing else. **`db push --linked` refuses an out-of-order migration** — verified 2026-10-31 with `db push --linked --dry-run` at #23's merge commit: `Found local migration files to be inserted before the last migration on remote database. Rerun the command with --include-all flag to apply these migrations`. A hand-written migration in a schema PR must therefore sort **after** everything applied on hosted; that check is what deleted `20261029000000_posture_grants.sql` (never applied: `migration list --linked` shows `20261030005109` as the only version, local and remote) rather than pushing it with `--include-all`. The platform facts a schema ticket inherits:

- Role settings are not declarable, so `[api] db-aggregates-enabled = false` is the shipped posture: no `count=`/`sum=` in PostgREST queries. [PostgREST: vertical and horizontal filtering](https://docs.postgrest.org/en/v13.1/references/api/tables_views.html#vertical-and-horizontal-filtering).
- [PostgREST: batched requests](https://docs.postgrest.org/en/v13.1/references/api/transactions.html#batched-requests) — two operations in one transaction is **refused** for v1; an atomic multi-table write is a **nested insert**, which PostgREST compiles to a single SQL statement, so it needs no `Prefer: transaction` dependency at all.
- Realtime streams only the tables a publication adds ([Supabase: Realtime publications](https://supabase.com/docs/guides/realtime/technical-references/configuration.md)), and a `DELETE` event carries only the replica identity. `item_store_tags` has a composite key, so it carries `replica identity full`. Publication membership is declared with the schema — pg-delta covers it ([Diff engines: pg-delta and migra](https://supabase.com/docs/guides/deployment/declarative-schema/diff-engines)), so #8 adds tables to the Realtime publication in a declarative file and CI mints it. `replica identity` was predicted to be outside pg-delta's covered list; **measured false 2026-11-02** - the generated tree carries `ALTER TABLE "public"."item_store_tags" REPLICA IDENTITY FULL;` in `public/tables/item_store_tags.sql`, manifest-tracked, with no `_custom/` directory in the tree (procedure step 10; the diff-engine list in the Appendix is the page that predicts this). `--strict-coverage` stays in CI as the tripwire for the next object the engine declines to model.
- Unsupported objects are reported as **coverage warnings** by `db schema declarative sync`, and `--strict-coverage` turns them into CI errors. Anything the engine declines to model lives in the reserved `supabase/schemas/_custom/` directory with its hand-written migration; `generate` never touches that directory, and a `generate` after files are added there overwrites nothing.
- `supabase gen types typescript --local --schema public --schema private` regenerates [`app/types/database.types.ts`](../../app/types/database.types.ts) from a stack that has the schema (`pnpm run db:types`; every schema PR that changes shape regenerates it, in CI, not by hand). Only the schemas passed to `--schema` get types, so a `private` function is untyped unless its schema is passed - the shipped file types `private.is_member`, which is the policy helper the app never calls, and it costs nothing to keep it honest. `--linked` works with no password for the same reason `db push` does; CI uses `--local`. `pnpm dlx oxfmt` formats the unformatted output by hand when a formatter is adopted - the repo has no formatter dependency today, so the generated file is committed as the CLI writes it.


## Applying changes: the hosted path, measured

The sequence #4 ran on 2026-11-02, with what surprised us attached. Reference names: hosted ref `ohbrawtgcyngyhaqtddy`, project `kinetic-lists` ([API](https://ohbrawtgcyngyhaqtddy.supabase.co), [Studio](https://supabase.com/dashboard/project/ohbrawtgcyngyhaqtddy)); branch `add-v1-schema` cut from `master` at `14028cf`; the tree commit `720d2d2`, the types commit `4a67213`. The Docker symptom all of these steps work around: Linux containers answered `500 Internal Server Error` on `npipe:////./pipe/dockerDesktopLinuxEngine`, `docker info` fails on the same pipe, and `supabase migration list --local` answers `ECONNREFUSED 127.0.0.1:54322`, so hosted is the database we can measure and a local stack is the one CI boots.

1. **Change the tree, or hand-write the baseline.** Steady state: edit `supabase/schemas`, keep `.pgdelta-export.json` consistent, never hand-write a migration. The one exception so far is the baseline itself - `20261101000000_add_v1_schema.sql` is the six seed files concatenated in load order, hand-derived because `sync` plans on a shadow stack Docker could not boot. If you hand-write, write the dependency order down first: the baseline's header is that plan, and four of the five things the push refused came from a dependency nobody had written - the grant posture, the sequence, `auth.uid()`, and every function body: the functions hang off `private.is_member` and off `auth.users` (ADR-0019's sign-up trigger `private.handle_new_user` is an `after insert on "auth"."users"` trigger, and `auth.users` is not ours to create), the sequence must exist before `lists."id"` uses it, and every policy's `(select "auth"."uid"())` needs `auth` readable - the initplan site is at `20261101000000_add_v1_schema.sql:150` (the `lists_select_by_member` policy), measured. That is why order is written down first, and why every hand-written migration must state its dependency walk.
2. **Apply it to hosted: `pnpm exec supabase db push --linked --yes`.** No database password - the CLI authenticates with the access token from `supabase login` (`Initialising login role...`, measured 2026-11-02); the password belongs to direct Postgres (`psql`, the Data API, Studio's SQL Editor). A failed push is a transaction, measured four times over: hosted sat at 0 tables and the same applied versions after each failure. `--linked` is the project, `--local` the dev stack, `--dry-run` prints the plan without applying. A version that sorts before an applied one makes every later push fail (`new migration ... proposed version ... must be greater than latest`), which is why the `revoke all on all ...` statement is a `default_privileges.sql` rule and not an early migration: the baseline's own header cites that refusal.
3. **Apply it to a local stack, in isolation: `pnpm exec supabase db reset`.** `db reset` drops the local database and replays seeds then every migration in `supabase/migrations/` (config.toml's `[db.seed].sql_paths` = `["./supabase/seed.sql"]`), so a migration that only works on a database with history is caught here. Not run on this machine, for the Docker reason above; it is #4's CI harness, alongside `lint`, `advisors` and `--strict-coverage`.
4. **`db push` is the only check that validates plpgsql - a parse check validates nothing.** `pip install pglast` then `from pglast import parse_sql` (there is no `pglast.Parser`) answers that the baseline is valid SQL, and it accepted every one of the five statements the push then refused; Postgres rejects at `create function` what a parser accepts, so pl-deps and pglast tell you nothing about bodies. The push names the statement (`At statement: N`) under `--debug`, which is why the header numbers them:

   ```bash
   pnpm exec supabase db push --linked --yes --debug 2>&1 | grep -A2 "At statement"
   ```

5. **Run both gates on the shape, not just the bodies.** `supabase db lint --from-md` prints findings as Markdown ([CLI: db lint](https://supabase.com/docs/reference/cli/supabase-db-lint)), and it needs the schema loaded on a stack ([local development](https://supabase.com/docs/guides/local-development/cli/getting-started)). Run against the hosted tree as it stood 2026-11-03, lint answered 69 fail / 125 pass / 226 ignore with 3 warnings - and every finding it reported is about a function body: **it does not see grants, policies, tables, views, indexes, triggers, columns, types, extensions, publications, privileges, schemas, RLS, sequences, partitions, materialized views, events, functions, or anything else that is not a plpgsql body** - the shape inventory lives in our register below and the `db advisors` run beside it ([Supabase: Lint rules](https://supabase.com/docs/guides/deployment/database-advisors) is the rule list its `--ignore-rules` flag takes). Neither gate is wired into `package.json` today: the CI job is #4's harness, and it reads its rule codes from the register below. `supabase db advisors` prints the advisory registry Studio's Advisor rules page runs against: `--from-md` for Markdown, `--pretty`, and `--ignore-rules <codes>`; measured on 2026-11-02, all of its findings were 0028 (unpinned `search_path`) and 0029 (`security definer` function granted to `anon`/`authenticated`) - our registered exceptions, so the shipped rule is "the gate runs clean of the rules 0020/0028/0029, with the rows above as the recorded reason". Its registry list is [Supabase: database advisors](https://supabase.com/docs/guides/deployment/database-advisors); the CLI's `--ignore-rules` is the auditable half, and a CI rule-code list in a `package.json` is the half a reviewer can read.
6. **Record a suppression where the repo can see it.** Supabase's advisor controls are Supabase Studio's **Advisor rules** page, whose suppression list lives server-side ([Advisors](https://supabase.com/docs/guides/database/advisors)); the CLI has no advisor-suppression command today. A suppression kept where the repo cannot see it is a claim no test can check. So a rule that is intentional for us gets **both**: its code in `db lint`'s `--ignore-rules` flag, and a row in the register above naming the object, the rule, and what replaces the warning. The register carries the suppression as an auditable list; CI reads the list from the register row and passes it via the CI variable, so CI runs `db lint` on the schema with no rule codes in a `package.json`.
7. **Read the grant surface from `information_schema`, not from a dashboard.** The two queries that answer "what can the phone actually do" run on hosted in seconds (`db query --linked`; the CLI's SQL execution is the Data API under the hood, so write one statement per call - it splits on `;` and does not understand a dollar-quoted body, which is why plpgsql bodies are tested by push, not here):

   ```postgres
   select "r"."grantee", "r"."routine_name", "array_agg"("r"."privilege_type" order by "r"."privilege_type") as "privs"
   from "information_schema"."routine_privileges" "r"
   where "r"."routine_schema" = 'public' group by 1, 2 order by 2, 1;

   select "t"."table_name", "t"."grantee", "array_agg"("t"."privilege_type" order by "t"."privilege_type") as "privs"
   from "information_schema"."table_privileges" "t"
   where "t"."table_schema" = 'public' group by 1, 2 order by 1, 2;
   ```

   Exclude `auth`, `storage`, `realtime`, `vault`, `extensions`, and the Supabase-managed tiers (`supabase_auth_admin`, `supabase_functions_admin`, `service_role`, `postgres`) when the question is about the browser roles. The grant matrix in section 5 is step 7's output, and it is the only place the DML verbs are written down.
8. **Read the constraints, and the keys they imply:** `pg_constraint` names everything the shape rests on:

   ```postgres
   select "c"."conname", "c"."contype", "rel"."relname" as "table",
          "pg_get_constraintdef"("c"."oid") as "def"
   from "pg_catalog"."pg_constraint" "c"
   join "pg_catalog"."pg_class" "rel" on "rel"."oid" = "c"."conrelid"
   join "pg_catalog"."pg_namespace" "ns" on "ns"."oid" = "rel"."relnamespace"
   where "ns"."nspname" = 'public' order by "rel"."relname", "c"."conname";
   ```

   The five checks ADR-0023 names - unique pair keys, cascades pointing at the parent (`store_locations(store_id) -> stores(household_id, id)`, `purchase_lines(purchase_id) -> purchases(household_id, id)`, `item_store_tags(item_id, store_id) -> items(household_id, item_id)`), the immutability triggers, no cascades off `auth.users` (the sign-up trigger is `after insert` on `auth.users` and owns no reference), and the erasers' cascade - are all read here, with the triggers beside them in `pg_trigger`.
9. **Read the policy expressions: `pg_policies`.** `select "schemaname", "tablename", "policyname", "cmd", "qual", "with_check" from "pg_policies" where "schemaname" = 'public' order by "tablename", "policyname"` lists the 32 policies with live row-level security ([PostgreSQL: CREATE POLICY](https://www.postgresql.org/docs/current/sql-createrole.html), and RLS is a Postgres feature Supabase turns on - [Supabase: Engineering Decisions](https://supabase.com/docs/guides/database/postgres/row-level-security)). Measure with a request carrying an `authenticated` JWT before believing a grant matrix; the JWT carries `role`, `sub` and `aud`, and PostgREST decides the role from the token. Tenancy goes one step further: `private.is_member` hides the `auth` read in a function body, which is why lint's 0003 is satisfied and the grant story (step 7) is the whole answer.
10. **Snapshot the tree, then commit it: `pnpm exec supabase db schema declarative generate --linked --overwrite`.** This is the step that makes the tree generated output rather than authored source. The regenerated tree is 31 files plus `.pgdelta-export.json`, whose top-level keys are `formatVersion` (1), `redactSecrets` (true), `scope` (`"database"`), `profile` (`"supabase"`), `defaultOwner` (`"postgres"`), `loadOrder` and `files` - **both 31 entries, both flat lists of file paths**, `files` starting `_cluster/extensions/pgcrypto.sql`, `loadOrder` opening `private/schema.sql`, `public/schema.sql`, `public/adp_wipes.sql` and closing `public/default_privileges.sql`. `loadOrder` is the dependency order the engine computed against the database it read, and it is migration execution order - filenames only, no statement counts. `adp_wipes.sql` is 3rd in `loadOrder`, `default_privileges.sql` last, and `_custom/` is a directory the engine reads when it declines to model something. Regenerate after **every** push: the tree is the input to `db schema declarative sync`, so it must be the tree that the last commit shipped. `db pull --managed-pg-delta-schemas` is the same write with a diff preview first, and lint/advisors read the same tree ([declarative schema](https://supabase.com/docs/guides/deployment/declarative-schema), [declarative workflow](https://supabase.com/docs/guides/deployment/declarative-schema/declarative-workflow)).
11. **Generate types, in the shape the app types against: `supabase gen types typescript --local --schema public --schema private > app/types/database.types.ts`** (`pnpm run db:types`; `--linked` needs no password, same as step 2). Then `pnpm dlx oxfmt` on the unformatted output. Only schemas passed with `--schema` get types; the shipped file carries `private.is_member` (the policy helper the app never calls, kept honest for free) and `public.uuidv7`. Regenerate it in CI on every schema PR that changes shape - the 708-line file at `4a67213` is generated output, and the drift check is the diff it produces in CI, not a hand edit.
12. **The sequence, validated.** 1. `db start` (Docker, needed by `reset`), 2. seed (config.toml's `sql_paths` = the one seed file), 3. migrations in `supabase/migrations/`, 4. `lint`, 5. `db advisors`, 6. `gen types` - run in that order on a container, with lint running after the seed so the seed's grants exist for lint to see. The order is not style: it is what makes an empty database, not a half-built one, answer your migration.
13. **The demo table's history, exactly.** `20261030005109_create_lists_table.sql` is v0 applied history (hosted has the version, and an insert-only migration sorting before an applied one is refused, so it stays as it is). `20261031000000_retire_demo_list.sql` - one statement, [`drop table if exists "public"."lists"`](../../migrations/20261031000000_retire_demo_list.sql) - retires it, retirement living in a migration for the reason in section 4. The v1 baseline then **creates a `lists` table with the same name**: the tree's `public/tables/lists.sql` is the v1 List (ADR-0009's `household_id`, pair key, cascade chain from `list_items`), not the demo table, so `migration list` + the tree tell the difference and the filenames do not. Measured on hosted 2026-11-03, `public` is 12 tables + 2 views - arrivals, household_invites, household_members, households, item_store_tags, items, list_items, lists, purchase_lines, purchases, store_locations, stores, plus `roster_items`/`roster_stores` - and **no demo table**: the 2026-11-02 tree's `public/tables/demo_shopping_list.sql` (the Studio wizard's table, present in the 2026-10-31 pull) is gone from the 2026-11-03 regeneration, and with it the `security-invoker` finding lint reported against it. `generate --overwrite` preserves untracked files with a warning, so a regeneration is not a clean room: to be sure nothing stale survives, remove `supabase/schemas` and regenerate, then check `.pgdelta-export.json` against the directory - 31 files, 31 `files` entries, 31 in `loadOrder`, and no `demo` path in the manifest, measured. This matters beyond tidiness: `sync` reads `supabase/schemas/**/*.sql` recursively, so a stale file for a dropped table plans its `create table`.
14. **Tree commits before types, as two commits** (`720d2d2` then `4a67213`): the tree is the input to `sync`/`lint`/`advisors`, the types are the app's view of the result; generated output that changes the app's types is a schema change and deserves its own commit. A PR that changes only generated output - types, tree - is the drift check ADOPT-5 names: `sync -f supabase/schemas --no-apply` against the snapshot must plan nothing, and a types-only diff in CI is the same signal, one step later.
15. **What the next ticket inherits from this baseline** (measured on hosted 2026-11-03, after the repair push): 12 tables, 2 security-invoker views, 11 triggers, 32 policies, 27 index statements (26 live), 1 sequence, the grants per table per role recorded in section 5, the definer census, the retired `lists`, `default_privileges.sql` as the ADP posture carried in the tree, and all of it declared in the generated tree - which means the next schema ticket edits 31 files in `supabase/schemas`, pushes, regenerates the tree and the types, and reads this procedure again.
16. **A fix appends; applied history never re-runs.** `20261031000000_retire_demo_list.sql` and `20261101000000_add_v1_schema.sql` are applied, so editing their files cannot change hosted - and `20261101000000_add_v1_schema.sql` carries the sign-up trigger, `is_member`, and the three RPCs, which is why a repair to any of them is a new file and not an edit. Everything the review of the baseline found landed as `20261103000000_open_the_policy_verbs.sql`, pushed with the rest (measured: `migration list --linked` shows four versions, local == remote; `preview_invitation` answers `{"state":"missing"}` to a minted uuid and `join_household` raises its 28000 guard, which proves the re-declared bodies compile). Two mechanics that step makes necessary: renaming a column means re-declaring every function body that names it, and `create or replace function` is the tool for it - it keeps the owner and the function's grants (the ACL survives), and the re-declared body re-states `set search_path TO 'pg_catalog'` because the printer's output is what the tree carries.
