# Advisors, lints, and the hosted database's out-of-band steps

How schema work in this repo passes its gates. [ADR-0023](../adr/0023-the-v1-schema-is-ten-household-owned-tables-under-pair-keys-with-three-granted-definer-rpcs-as-its-whole-privileged-surface.md) decided the schema; this file is what a ticket touching `supabase/` must know to ship it. Facts below were verified against the Supabase docs and CLI 2.122.0 for [ticket #3](https://github.com/justintaddei/kinetic-lists/issues/3).

## The two gates, and what each sees

- `supabase db lint` runs **`plpgsql_check` over function bodies only**. It does not see tables, policies, grants, views, triggers or indexes. It is a plpgsql linter, nothing more.
- `supabase db advisors` prints the Supabase **advisor** findings — the security and performance rules [the advisory registry](https://supabase.com/docs/guides/database/advisors) names (`0001`…`0030`), the same registry Supabase Studio's **Advisor rules** page shows against the hosted project, since [2026-06](https://supabase.com/changelog.md/2026-06-22-advisor-api) on `plpgsql_check` findings too.
- Both gates need a shadow database, so both run in CI on a local stack ([#4](https://github.com/justintaddei/kinetic-lists/issues/4)), and nothing about them can be checked by a `git commit` alone.

## The suppression contract

`preview_invitation` is granted to `anon`, and the three RPCs are granted to `authenticated`; all three are `security definer`. Lint `0029` fires on them **by design** — [ADR-0023](../adr/0023-the-v1-schema-is-ten-household-owned-tables-under-pair-keys-with-three-granted-definer-rpcs-as-its-whole-privileged-surface.md): *the grant is the app's API surface; a definer the phone cannot call is not an API.* The set is closed: nothing else gets a grant, and the app's PostgREST-exposed functions stay exactly:

- `public.buy_basket(uuid, uuid, date, text)` → `authenticated`
- `public.join_household(uuid)` → `authenticated`
- `public.preview_invitation(uuid)` → `anon`, `authenticated`

Suppressions live in the hosted project, not in this repo: the CLI has no in-repo expression for an advisory suppression, so they are applied per object on the hosted project's **Advisor rules** page (Supabase Studio → **Database → Advisor rules**), and re-checked after every `db push`. They are out-of-band state on hosted, so:

- Suppressions are **not** reapplied by `db reset` (that is a local-stack operation — it is *how* #4's CI builds a shadow database, and it touches no hosted project from a checkout. The hosted database is never reset from a checkout; it moves by migration.)
- #4's CI gate is: `db lint` clean, `supabase db advisors` reviewed against this register, and `db schema declarative sync --dry-run` producing the expected migration.
- A new `security definer` function reaching `anon`/`authenticated` is a decision, and joins this list by being written here first, in the same PR that adds it.

## The declarative schema and the demo table's retirement

`supabase/schemas/*.sql` is the source of truth (`[experimental.pgdelta] enabled = true` in [`supabase/config.toml`](../../supabase/config.toml)), and `supabase db schema declarative sync` mints a migration from the diff — `--dry-run` to read the SQL, `--no-apply` to mint it in CI without touching a database, `-f` when a hand-written migration must be allowed alongside, and **`--strict-coverage` in CI** so any object the engine declines to model fails the build instead of quietly disappearing.

- **File order is automatic under pg-delta** - the CLI orders the declarative files by statement dependency, and `[db.migrations].schema_paths` is ignored (it warns when set). The `01_`…`06_` prefixes in `supabase/schemas/` are reading order for humans, not load order.
- The grant posture is the named example of an object the engine cannot diff, and it is shipped **twice on purpose**: [`supabase/schemas/_custom/posture.sql`](../../supabase/schemas/_custom/posture.sql) (so a shadow database is built in the same shape) and [`supabase/migrations/20261029000000_posture_grants.sql`](../../migrations/20261029000000_posture_grants.sql) (so hosted reaches it). The migration **sorts before** every migration that creates a `public` object — that is what keeps `db reset` and every later `sync` reproducible; a `_custom` change whose migration sorts late breaks both. When one file changes, the other changes in the same PR.

- The demo `lists` table's declarative file is deleted; **its migration file stays in `supabase/migrations/`**, because a migration in history is history, and `db pull` requires every remote migration to have a local file. The table retires through a generated `drop table` migration minted from the declarative diff, keeping history append-only.
- Unmodeled objects live in the reserved `supabase/schemas/_custom/`, with their hand-written migration: `db schema declarative sync` skips that directory, and unmodeled objects are never deleted from the database.
- **Baseline first, in this order, on the hosted project** (an operator step, taken before the first sync, in one session — a hosted `db pull --help` is unhelpful mid-session: `db pull` needs a baseline, and a baseline needs a clean declarative state): the app holds no user data today, so
  1. `supabase db reset --experimental --linked` (drop + re-apply history — clears `supabase_migrations.schema_migrations` and the `lists` table). Safe only because v1 has no user data; it is a one-time baseline, not a routine; the hosted database is never reset from a checkout afterwards.
  2. apply the grant posture (§below) once, so the snapshot baseline records the v1 grant state, not Supabase's default one;
  3. `supabase db pull --declarative` takes the snapshot baseline into `supabase/migrations/`;
  4. the declarative files land as one generated migration (#4's sync), committed and pushed.

## Grant posture, and the steps no declarative file can express

Signed out, the app reads nothing except `preview_invitation`. Supabase's defaults grant `anon` and `authenticated` broadly on `public`, and CLI 2.122.0 has no declarable `alter default privileges`; [the migration page](https://supabase.com/docs/guides/deployment/managing-your-database-schema.md#declarative-schema) says to put such objects in `supabase/schemas/_custom/` with a hand-written migration. So the anon revokes below run **before** declarative sync, once, on hosted, and are re-checked after a `db reset` on any shadow stack:

```sql
revoke all on all tables in schema "public" from "anon";
revoke all on all sequences in schema "public" from "anon";
revoke all on all functions in schema "public" from "anon", public;

alter default privileges in schema "public" revoke select on tables from "anon";
alter default privileges in schema "public" revoke usage on sequences from "anon";
alter default privileges in schema "public" revoke execute on functions from "anon", public;
```

These are exactly the statements of [`supabase/schemas/_custom/posture.sql`](../../supabase/schemas/_custom/posture.sql) and [`supabase/migrations/20261029000000_posture_grants.sql`](../../migrations/20261029000000_posture_grants.sql) — the three files carry the same six statements, and the revokes are idempotent (an empty database is unchanged by them). `public` is in the function revokes because Postgres' own default grants `execute` to `PUBLIC`.

`private` carries no grants at all beyond `usage` for `authenticated` and `supabase_auth_admin`, so it has no HTTP surface: PostgREST reaches schemas listed in `[api] schemas = ["public", "graphql_public"]` and nothing else. Two more platform facts a schema ticket inherits:

- Role settings are not declarable, so `[api] db-aggregates-enabled = false` is the shipped posture: no `count=`/`sum=` in PostgREST queries. [PostgREST: vertical and horizontal filtering](https://docs.postgrest.org/en/v13.1/references/api/tables_views.html#vertical-and-horizontal-filtering).
- [PostgREST: batched requests](https://docs.postgrest.org/en/v13.1/references/api/transactions.html#batched-requests) — two operations in one transaction is **refused** for v1; an atomic multi-table write is a **nested insert**, which PostgREST compiles to a single SQL statement, so it needs no `Prefer: transaction` dependency at all.
- Realtime streams only the tables a publication adds ([Supabase: Realtime publications](https://supabase.com/docs/guides/realtime/technical-references/configuration.md)), and a `DELETE` event carries only the replica identity. `item_store_tags` has a composite key, so it carries `replica identity full`. Publication membership is declared with the schema — pg-delta covers it ([Diff engines: pg-delta and migra](https://supabase.com/docs/guides/deployment/declarative-schema/diff-engines)), so #8 adds tables to the Realtime publication in a declarative file and CI mints it. `replica identity` is not on pg-delta's covered list, so expect a coverage warning on that statement and pass `--strict-coverage` in CI; if it is refused, it goes in `supabase/schemas/_custom/` with a hand-written migration sorting before the generated migration that creates its table.
- Unsupported objects are reported as **coverage warnings** by `db schema declarative sync`, and `--strict-coverage` turns them into CI errors. Anything the engine declines to model lives in the reserved `supabase/schemas/_custom/` directory with its hand-written migration; `generate` never touches that directory, and a `generate` after files are added there overwrites nothing.
- `supabase db gen-types` regenerates [`app/types/database.types.ts`](../../app/types/database.types.ts) from a stack that has the schema; every schema PR that changes shape regenerates it, in CI, not by hand.
