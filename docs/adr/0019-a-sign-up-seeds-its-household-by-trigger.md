# A sign-up seeds its Household with a trigger on `auth.users`

> **Amends [ADR-0009](0009-households-own-everything.md):** "created at sign-up" has a mechanism — an `after insert` trigger on `auth.users`, owned by migrations, and nothing in the app writes a Household.
>
> **Amended by [ADR-0014](0014-household-membership-is-granted-by-an-invitation-token.md) reading:** the **Display Name** seed runs inside that trigger, and "the auto-created Household is permanent" is now **a Household is gone when its last Membership is**.

[ADR-0009](0009-households-own-everything.md) said a Household is created at sign-up, and [ADR-0014](0014-household-membership-is-granted-by-an-invitation-token.md) made the first Membership the root of every read in the app: tenancy filters through `private.household_ids_of_current_user()`, so a signed-in user with no Membership row sees an empty app and can never **Join** (Join tests *their own* Household for emptiness). We decided a `security definer` trigger function `private.handle_new_user()`, fired `after insert` on `auth.users`, writes both rows — the `households` row named **"My Household"** and the `household_members` row with the Display Name seeded from the sign-in provider — and that **no app code writes a Household at all**, so `private.ensure_my_household()` is not built and there is no first-request write.

The trigger wins on coverage, which is the whole question: GoTrue inserts `auth.users` on **every** account-creating path (email+password sign-up, OAuth sign-up, magic link/OTP for a new user, admin invite, Dashboard "Add user", `auth.admin.createUser`, the CLI admin commands), and its own code reloads the row expecting triggers to have run. A Nitro write with the secret key after `signUp` was rejected because the app has no sign-up call site to write it from (`login.vue` calls `signInWithOAuth` alone, `server/` is empty), it would hand the app a secret key that ADR-0006's shape keeps out of reach, and it misses every path that is not the app's own sign-up — OAuth's callback included. A deferred self-heal was rejected because it is a write on the app's hot path, a window where a real user has no Household, and a function whose whole job is to catch a case the trigger makes unreachable.

**How it is built.** The declaration lives in the declarative schema file (`supabase/schemas/`): pg-delta excludes Supabase-managed schemas but captures customizations on top of them, counting a trigger on `auth.users` as ours because its function lives outside `auth`, so `db schema declarative sync` keeps `supabase/schemas/` ground truth. The function is `security definer` with `set search_path = ''` and schema-qualified body references (lint `0011`), owned by `postgres`, which has `bypassrls` — that is what lets it write `public` tables whose RLS policies read the membership table, and it needs no policy of its own. Grants are explicit: `usage` on schema `private` and `execute` on the function to `supabase_auth_admin` (the role GoTrue inserts as, so the trigger needs it), `execute` revoked from `anon`, `authenticated` and `public`. **Rows live in `public`** (`households`, `household_members`); definer functions live in `private`, kept out of the API's exposed schemas — a definer function in an exposed schema is callable over `/rest/v1/rpc/<name>` by `anon` (lints `0028`/`0029`).

**Seeding, failure and lifetime.** The Display Name follows `GLOSSARY.md`'s chain, newest keys first: `raw_user_meta_data->>'name'` → `preferred_username` → `full_name`/`user_name` (the deprecated GitHub keys) → `split_part(NEW.email, '@', 1)`. The email local-part comes from the `NEW.email` column, never `identity_data`: at OAuth sign-up GoTrue writes the user row **before** creating the identity, so `auth.identities.identity_data` has no row at trigger time. The trigger has **no exception handler** — it runs in the same transaction as the `auth.users` insert, so a raising trigger aborts that sign-up. That is chosen deliberately over swallowing the error: with no self-heal to catch it, a swallowed failure is a signed-in user with a permanently empty app and nothing in the UI saying so. The trigger fires for every insert, with no `is_sso_user` or anonymous-account filter. `household_members.user_id` references `auth.users (id)` `on delete cascade` (the primary key only — lint `0021`: FKs to any other unique constraint of the `auth` schema block Supabase Auth's own migrations), and an `after delete` trigger on `household_members` deletes the Household that just lost its last Membership — [ADR-0017](0017-purchase-lines-reference-rows-and-every-delete-cascades.md)'s last-Purchase-Line pattern, applied to tenancy.

Accepted costs, and the facts this fixes for the schema: v1 **ships no backfill** for accounts that already exist on the hosted project, because the hosted project is cleared instead — a `after insert` trigger never touches rows that already exist, and DML cannot live in a declarative file anyway. `unique (user_id)` on `household_members` (one Household per user, ADR-0014), `households.name not null default 'My Household'`, the two triggers, the FK cascade, and the grants above are the schema shape #3 copies. The free win: `auth.admin.createUser({ email_confirm: true })` fires the trigger, so an E2E two-Member Household is two fixture users plus **Join** driven through the UI, with no Household code in the harness — and ADR-0014's refusal of a non-empty Household is testable only because every user is guaranteed a Household. Verified on the local stack first (`db reset`): Supabase's docs do not state that local and hosted `auth.users` ownership and privileges are identical.
