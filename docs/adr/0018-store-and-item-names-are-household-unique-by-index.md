# Store and Item names are Household-unique by index, and the join is an offer

[ADR-0013](0013-a-store-has-locations-and-its-coordinates-come-from-a-position.md) and `GLOSSARY.md` promise that "capturing an existing Store name adds a Location to it rather than minting a second Store", and ticket #7 made Item names unique per Household — while this ticket (#16) found the Store rule living **nowhere**: no index, no trigger, only #13's confirmation modal. Enforcement in the UI alone means two Members capturing "Walmart" in the same second mint two Stores, eggs tagged `walmart` split across them, and only a merge verb — ruled out of v1 — heals it. So: **`unique (household_id, lower(trim(name)))` on `stores`, the shape `items` already carries**, with the modal sheet offering the join and the index as the concurrency backstop. Two Members capture "Walmart" at once: one insert lands, the other takes a `23505` unique violation, and the app opens that as #13's join sheet, not as an error toast.

Rejected: **UI check only** (readable duplicates, unfixable without the merge verb v1 refuses to build); a **trigger that silently joins** the name, which kills the confirmation #13 settled on and hides which Location landed under which Store. Trim is not decoration: `lower()` alone leaves `"Walmart"` and `"Walmart "` as two Stores, and a mint sheet with a typed name can type both.

Consequences: the key is the **Household's**, not global, so two Households each keep their own Walmart (ADR-0011); #13's second option, "name it X as its own Store", means a *distinct* typed name, never a second identical Walmart; renames hit the same key, so renaming into an occupied name takes the same join offer; and because same-named Stores cannot exist, the merge case is always two **differently named** Stores ("Walmart" and "Walmart on 5th"), whose merge verb is out of v1 — deleting the loser is v1's answer (ADR-0017).
