# A Store has Locations, and its coordinates come from a Position

A Store used to carry its own coordinates and Geofence, which meant a Household with two Walmarts had two Stores that never merge, and the coordinates came from a Geoapify forward geocode (ADR-0007). v1 splits the two jobs the Store was doing — the **name you tag Items with** and **the place you stand in** — and drops geocoding entirely: a **Store** is the Household's tag namespace (Pickable, the Kinetic View's subject, may have no Location at all), and a **Location** carries the coordinates and the Geofence, created by a one-shot device **Position** when a Member buys or tags where they are standing, or typed in as lat/lng for a place not visited. We chose this because one geocode query is one naming act, and paying for it meant a key, a quota, a picker contract, an attribution obligation and a dead end on exactly the queries people type — the geocoder indexes *addresses*, while "Walmart" is a chain (chain retail is the Places/POI product; the geocoding endpoint has no POI type at all, and ambiguous names rank by popularity, not by where you are).

This supersedes [ADR-0007](0007-geoapify-is-the-geocoder.md): no geocoding API is called in v1 and no key is minted. It amends [ADR-0011](0011-stores-belong-to-a-household.md) (a Store still belongs to a Household; its Geofence now lives on the Location) and [ADR-0005](0005-arrival-is-client-side-and-only-suggests.md) (the client judges Inside against Locations; an Arrival records (Member, **Location**, time) and only suggests Picking that Location's Store).

Consequences: capturing an existing Store name **adds a Location** to that Store after a confirmation, so eggs tagged `walmart` show up at both Walmarts; a **Purchase** names the Store *and* the Location, and each **Purchase Line** snapshots both, so history survives renames and moves; a Purchase never names nothing — the Buy flow offers "name this shop" (typed name + Position) when no Store fits; Item capture offers existing Stores, "add store from where I am now", and **no Store Tag at all** for a freshly captured Item, so Tags arrive by shopping, never by browsing; a distant Store is a **bare Store** (name only, geofence-less) unless its coordinates are typed by hand. v1 ships **no map**: a pin picker with street and building detail needs a basemap and a key we declined to take on, so it graduates to its own ticket with Leaflet 1.9.4 (BSD-2, no WebGL dependency — MapLibre v6 requires WebGL2) against a building-aware raster basemap, and attribution obligations move from Geoapify to that basemap's terms.
