# The UI is shadcn-vue components copied into the app, on Tailwind v4, phone-first

> **Amends [ADR-0015](0015-store-tags-are-written-at-capture-and-an-arrival-selects-the-active-store.md) and [ADR-0010](0010-a-list-item-has-one-status.md) reading:** the surface called a **sheet** in those decisions and in tickets #13/#20 is the **Drawer** — a bottom sheet, `swipe-direction="down"`, never a centred dialog on a phone.

The app's screens are built from **shadcn-vue components copied into the repo**, on **Tailwind CSS v4**, in the shape the official shadcn-vue Nuxt guide prescribes: Tailwind is wired through `@tailwindcss/vite` (the guide's `@nuxtjs/tailwindcss` tab was rejected — that module's Tailwind v4 support stalled at a 2025 beta, latest stable 6.14.0 is v3-era), the entry is `app/assets/css/tailwind.css` (`@import "tailwindcss";` + `@import "tw-animate-css";` + `@import "shadcn-vue/tailwind.css";` — the style export resolves through the Vite plugin, so v1 never vendors a ~565-line base stylesheet), `shadcn-nuxt` is a Nuxt module with `componentDir: "~/components/ui"`, and the theme is the registry preset **`a2vfHFI`**, applied with `pnpm dlx shadcn-vue@latest init --preset a2vfHFI` (resolves to style `reka-luma`, base color **neutral**, Inter, lucide icons, `--radius: 0.625rem`, per the guide's rule that a preset carries base colour/fonts/registry colour and leaves the base style alone). Tailwind v4 is CSS-first: there is no `tailwind.config.js`, and theme tokens live in the entry's `@theme inline` block.

**`app/components/ui/**` is app-owned code.** The registry is the starting point, not a dependency: components arrive with `pnpm dlx shadcn-vue@latest add <name>` (registry dependencies come with them — `textarea` arrived as `input-group`'s dependency), keep their registry-stable names, and are edited as needed. v1's owned set is `alert-dialog`, `badge`, `button`, `card`, `checkbox`, `dialog`, `drawer`, `empty`, `input`, `input-group`, `label`, `scroll-area`, `select`, `separator`, `sonner`, `spinner`, `textarea`. **`sheet` is not in it:** shadcn-vue's `drawer` is the mobile bottom-sheet component, built on **reka UI's `Drawer` primitive (not vaul-vue)** — renamed in v2's breaking changelog, with `swipe-direction` replacing `direction`. The cost of owning the copy is upstream churn: registry changes land as merges we make by hand. Accepting that is the point — shadcn is a copy tool, not a component library, so no UI dependency sits between us and a screen.

**Screens use auto-import, with no import lines.** Nuxt resolves the copied components from `app/components/` by directory and export, so a screen writes `<UiButton>`; the component name comes from the copied directory's `index.ts` export, which is why sonner is **`<UiToaster>`** and not `<UiSonner>`. Icons (`@lucide/vue`), `cn` from `app/lib/utils.ts`, explicit values, and event payloads are written at the call site; composables (`useStorage`, `onClickOutside`, `useColorMode`) are auto-imported by `@vueuse/nuxt`. The visual language is **utility classes in the screens, tokens from the preset** — no hand-rolled `<style>` blocks and no app CSS beyond the entry (`index.vue`/`login.vue`/`confirm.vue` keep their scoped CSS until ticket #11 restyles them; Tailwind's preflight will shift them in the meantime).

**A phone is the design target, and desktop is the same column in a container — not a layout.** Targets are **44px** and controls sit in thumb reach, which the registry does not give for free: its default control height is `h-9` (**36px** — verified on `Button`, `Input`, `Select` trigger), `Button size="lg"` is `h-11` (44px), so the owned copy raises form controls to 44px. `viewport-fit=cover` is on the viewport meta and the safe-area utilities come from the `tailwindcss-safe-area` plugin (`pb-safe`, `pt-safe-offset-4`), since Tailwind v4 ships none; `theme-color` metas carry the light and dark surfaces. `app/plugins/ssr-width.ts` provides a reference width of **430** CSS px — the guide's own plugin, needed for components that branch on viewport width, and it takes the plugin-shaped form `provideSSRWidth(430, nuxtApp.vueApp)` because `provide()` outside `setup()` warns and provides nothing. Hover effects are welcome for desktop users, and **nothing critical is hidden behind hover**. Dark mode follows the system: the token block is declared under `@media (prefers-color-scheme: dark)`, with **no `.dark` class and no `@custom-variant dark`**, so Tailwind's default media-query `dark:` variant agrees with the tokens; `color-scheme` is set per scheme. A user theme control is deferred to its own card, and when it arrives it takes @vueuse's `useColorMode` shape, re-declaring the same tokens under a `.dark` class as a two-place change.

**Two things the browser check settled, because they shape E2E seams.** Overlay dismissal is not uniform: a Drawer dismisses on Escape **only when `modal` is set** (non-modal: swipe, the Close control, outside-press only), and in headless Chromium an Alert Dialog stayed open through Escape with focus inside — so v1's confirmations always carry a labelled **Cancel** and **Delete** action, sheets always carry a labelled Close, and **tests dismiss by clicking, never by pressing Escape**. The Playwright seam is **role + accessible name** (the Drawer reports `role="dialog"` named by its `DrawerTitle`, the Alert Dialog `role="alertdialog"` named by its title — the seam finds both), with `data-slot="…"` attributes used only when roles are genuinely ambiguous. That seam is what ticket #4's tests use, and the prototype branch's screens are not promoted: v1 builds its Capture, Kinetic View, and confirmation surfaces from this foundation, from decisions, not from prototype code.
