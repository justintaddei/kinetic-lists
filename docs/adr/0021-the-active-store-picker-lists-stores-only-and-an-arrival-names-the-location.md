# The Active Store picker lists Stores only, and the Location a Buy records is the one an Arrival named

> **Amends [ADR-0016](0016-buy-takes-the-whole-basket-and-claims-rows-on-the-servers-clock.md):** Buy opens **no Location sheet**. The Location a Purchase records is the **Standing Location** — the Location of the Member's most recent **Arrival** — and a Buy with no Standing Location records none (`purchases.location_id` NULL, which ADR-0016 already made legal).
> **Amends [ADR-0015](0015-store-tags-are-written-at-capture-and-an-arrival-selects-the-active-store.md):** "their Pick stands until the next Arrival" stands **on the device they Picked on** — Active Store and Standing Location are browser state, not rows.

Wayfinder ticket [#19](https://github.com/justintaddei/kinetic-lists/issues/19) had to make the header's **Store picker** behave at Household scale: the prototype verified it at three Stores ([#13](https://github.com/justintaddei/kinetic-lists/issues/13), shape D), and 25 is a wall. We chose the **Store list, and nothing else**: rows are Stores, pinned Active-Store-first, then alphabetical, each row the Store name and its Location count (`Walmart · 2 Locations`, `Trader Joe's · No Locations`), the Active row ticked. It narrows by a **filter field that appears at six Stores** — substring on Store names, Household rows only (ADR-0013's naming problem, not the world's). It orders by nothing else: **no recency, no "Needs most here", no nearest-Location-first, no Needed counts.** A Household is capped by nothing; ten Stores is the design target and twenty-five stays usable.

The ordering is that plain because **the Active Store is remembered in the browser, per Member, not in a row.** Picking is a view selector on a Household-shared dataset, and the app that restores it is the one that reads it: a Member's Pick stands on that device, and a new device opens where an **Arrival** puts it, or at **no Active Store**. [ADR-0017](0017-purchase-lines-reference-rows-and-every-delete-cascades.md)'s ruling that history is read by no one is what makes the cheap answer safe — nothing in v1 reads a Pick, so nothing needs a `Picked` act, a `picked_store` column, or the recency table a "recently here first" list requires.

**A Location is not hand-Picked in v1.** The reason a Household names a Store is to see which **Items** it Needs there; the reason a **Location** exists is to make an **Arrival** fire. So the picker stops at the Store, and the one Location the app knows is the **Standing Location**: the Location of the Member's most recent Arrival, which names the Location a Buy records. A hand-Pick **clears it** — picking Walmart by name is not standing at Central St — so a Member who hand-Picks a Store with three Locations **Buys silently and records no Location**. A **Bare Store**'s Buy keeps ADR-0016's ask, phrased as the offer it is: *"add this place as a Location for Walmart?"*, declining legal, the **Position** in hand (ADR-0013). This is why the header shows **no Location**, and why a Location needs no name: the only place a Location speaks is the mint sheet's confirm, and nameless lat/lng rows are not shown to a shopper.

**The mint is one sheet with three doors.** A Household owning **no Store has no Active Store** (ADR-0016), and there the header's control opens the **mint sheet directly** — an empty list offers nothing to Pick, so the picker never opens. Buy's gate ("name this shop") opens the same sheet, and the picker keeps a sticky `+ Store from where I am` entry outside the scrolling rows, so a 25-Store wall is never mint-proof; the filter's typed name carries into it, and a name that matches opens the name-join sheet (ADR-0018).

**The picker is for Picking only.** Store Tags stay chips on the capture form, the Item's screen and the Store's screen (ADR-0015), and the mint sheet is shared by capture's `+ Add a store from where I am now` — so there is no Store-picker variant per job, and no Store list that edits Tags.

Consequences by ticket: **#3** gets "no `active_store` column, no recency table, no Location label column", plus the RPC guard `buy_basket`'s `location_id` must belong to `store_id`; **#6**'s watch sets the Active Store **and names the Standing Location**; **#11** prototypes these states (tick + A–Z, the six-Store filter, the mint as the header's first door, the Bare Store's Buy ask, a 25-Store sheet) and **#21** styles them; **#4** gets a role-and-name seam over the Drawer plus a 25-Store fixture; a cascade in **#20** that erases the Standing Location is answered by the same null fall as a deleted Active Store, no re-Pick rule.

Rejected, and why: **recent-first** (needs a row per Member to order a view selector); **Needs-most-first** (a ranking a picker has no data to defend — the Kinetic View is where Needs are shown); **drill-in to Locations** (needs the Location *name* ADR-0017 retired, and a hand-Picked Location would name a Buy the Member is not standing at); **Buy's Location sheet** (same: a nameless list of coordinates, no map, answering a question the Position already answered); **a Location line in the header** ("Walmart · 42.10154, -72.5811" is unreadable, and showing a Location means naming one).
