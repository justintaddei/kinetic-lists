# Purchase Lines reference rows, and every delete cascades

[ADR-0004](0004-purchases-are-append-only-snapshots.md) copied Item name, Quantity and Store onto every **Purchase Line** so "what did we buy at Walmart in March" survived renames and deletions, and [ADR-0013](0013-a-store-has-locations-and-its-coordinates-come-from-a-position.md) added the Location name, "surviving renames, moves and deletions". Then [ADR-0016](0016-buy-takes-the-whole-basket-and-claims-rows-on-the-servers-clock.md) shipped **no Purchase-history screen**: the **Kinetic View** shows **Needed** rows only, so in v1 no Member ever reads a **Purchase**. A snapshot exists to protect a read that does not exist, and its cost lands on the ordinary act of tidying a Household — delete the Store you renamed, delete the Item you typed wrong — which the snapshot rule turns into a row that can never be deleted. So: **a Purchase Line references the Item and the Store by id and stores no copied text**, and **every delete cascades** — an **Item** takes its Purchase Lines, its live **List Item** rows and its Store Tags; a **Store** takes its **Locations** (and their **Arrivals**), its Store Tags, its **Purchases** and their Lines; a **Location** takes the Purchases that named it. All three delete verbs (Store, Location, Item) and both rename verbs (Store, Item) ship in v1. We chose this because **history is disposable in v1** — nothing in v1 recommends, suggests, ranks, or reports from a Purchase, so data describing a name the Household has thrown away is worth throwing away with it, and v1 should not build machinery to protect it.

Rejected: **keeping the snapshots** (they never outlive their parent once deletes cascade, so the copy columns pay rent only on renames, and five text columns is a real cost on the app's largest table); **`RESTRICT` on Items** (a captured Item becomes permanent the moment it is bought once, and the catalogue is exactly where a Household's typos accumulate); **`SET NULL` on `purchase_lines.item_id`** (history outliving the Item it describes, with no copied text left to read it by, since the references read a row that is gone).

Consequences:

- **A cascade reaches live shared rows, and FK cascade is not checked by RLS.** A Member's delete of a Store erases **List Item** rows their policies would never let them delete directly, so the delete sheet is the only place a Member learns the cost, and it has to count what it erases.
- **ADR-0016's "every Purchase has ≥1 Purchase Line" is enforced after the write too**: an after-delete trigger deletes a Purchase whose last Line was cascaded away, so a trip never stands there having bought nothing.
- **A Line dies with its Item, not with its List Item**: deleting a List erases standing rows and touches no history.
- **Renames are free** — history reads the name the row carries today — so `stores.name` and `items.name` are editable and a rename re-labels the Household's past with no migration (the name key itself is ADR-0018).
- Cascading FKs need a supporting index on the referencing side, which grows #3's index list: `purchases.store_id`, `purchases.location_id`, `purchase_lines.item_id`, `store_locations.store_id`, `item_store_tags.store_id`, `list_items.item_id`.
- Deleting the Store a Member is standing at drops the Household to **no Active Store** — the same state ADR-0016 invented for a fresh Household, reused rather than joined to a new one. A Store whose last Location is deleted is a **bare Store**, which no Arrival can ever select.
- The map's rule that v1's history is data-only is now **load-bearing**: cascade, references and merge-free hygiene all stand on there being no history screen.
